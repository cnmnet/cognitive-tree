# 设计决策

## 2026-06-01 DR-001：高效查询方案 V2.0 —— 无向量库，三剑客为核心

**背景**：系统需要检索晶体卡片、孔洞、认知基准案例、外部追踪摘要等文本内容。传统向量数据库（RAG）存在成本高、延迟高、幻觉风险、依赖外部服务等问题，不符合系统“简单优先于复杂”和“数据不出域”的原则。

**核心原则**：
- 大模型负责“翻译”（自然语言 → 关键词/正则表达式）
- 三剑客（grep/awk/sed）负责“执行”（极速精确匹配）
- 文件系统负责“索引层”（预生成索引文件）
- 向量数据库彻底下岗，仅在极少数模糊语义兜底场景作为可选后备

**数据预处理**：
- 每条晶体/孔洞/案例入库时，自动生成一组**确定性索引标签**，存储在单独的索引文件（如`index_crystals.txt`）中
- 索引标签来源：标题核心名词短语 + 内容核心名词短语 + 链接的晶体/原则ID
- 预期索引规模：500条晶体 + 30个孔洞 + 若干案例，总行数约600行，grep扫描时间 <10ms

**查询流程（四步，硬编码到脚本）**：
1. **大模型生成关键词**：调用轻量模型将用户自然语言问题转换为3-5个关键词
2. **grep/awk多文件并行匹配**：`grep -E "关键词1|关键词2" index_*.txt`，按命中关键词数量初步排序
3. **结果合并与精排**：取Top 10条原始内容，按命中数降序排列
4. **大模型二次精读**：在Top 10内容上生成最终答案，不编造

**对模糊语义的兜底**：
- 自动扩展同义词（大模型生成）
- 可选HyDE（生成假设答案后再提取关键词）
- 若仍无命中，返回“未找到直接相关内容，建议手动检索冷库”

**与系统现有机制的集成**：
- 每日外部追踪：抓取的新闻/论文摘要入库时生成索引，次日可被命中
- Wondering问题生成：先检索是否有现成答案，避免重复提问
- L0/L1热端预加载：L0（3条种子孔洞）+ L1（≤47条晶体）内容直接常驻内存，grep无需磁盘I/O

**性能与成本**：
| 环节 | 耗时 | 成本 |
|------|------|------|
| 大模型生成关键词 | <500ms | 忽略不计 |
| grep/awk扫描（600行） | <10ms | 0 |
| 大模型精读（2000 token） | 1-2s | ~0.005元 |
| **总计** | **<3s** | **极低** |

**局限性**：
- 只能处理纯文本（系统所有数据均为纯文本，无PDF/图片等需求）
- 依赖大模型生成关键词的质量，同义词覆盖可能不足
- 组合查询（AND/OR）需多次grep或简单DSL，复杂嵌套建议拆分为多轮对话

**未来演进**：
- 当晶体突破1000条时，替换`grep`为`ripgrep`（更快）
- 若关键词命中率下降，可在索引层引入轻量BM25排序（无需向量库）

**结论**：此方案完全符合卢氏注意力边界原则（注意力调度优先）和简单优先原则，是当前系统规模下的最优解。向量数据库不再是必要组件。
